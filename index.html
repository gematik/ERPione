1. Introduction

This document describes the architecture of Erpione, a modern open source e-Health platform simulator. Erpione’s primary goal is to provide a comprehensive simulation environment for E-Rezept client systems. This enables vendors to test their applications by simulating the missing bits of the E-Rezept workflow, such as the PVS, AVS, and NCPeH systems. Erpione allows vendors to focus on their own application logic without needing access to other real complementary systems, which are often unavailable or impractical for testing purposes.

1.1. Requirements

Erpione must provide the following core capabilities to support its business goals:

  • Simulate the behaviour and interactions of complementary systems in the E-Rezept workflow. These systems include PVS (Praxisverwaltungssystem), AVS (Apothekenverwaltungssystem), and NCPeH (National Contact Point for eHealth).

  • End-to-end testing of E-Rezept client systems must be possible even when real complementary systems are not available.

  • It is essential to abstract the complexity of these systems so that vendors can develop and test their own solutions efficiently.

The primary users are vendors developing client systems for E-Rezept, ePA, and other solutions that interact with the E-Rezept backend service.

1.1.1. Reference to E-Rezept

Erpione is designed as a 'Primärsystem-Simulator' based on the E-Rezept system specifications. Erpione’s requirements and functionalities align with the following official E-Rezept documents and resources:

  • Systemspezifisches Konzept E-Rezept

  • Spezifikation E-Rezept-Fachdienst

  • Spezifikation Datenmodell E-Rezept

  • Implementierungsleitfaden Primärsysteme – E-Rezept

These documents serve as the authoritative basis for the simulation logic and interoperability provided by Erpione. For detailed technical and process requirements, please refer to the official E-Rezept documentation at gemspec.gematik.de (or the current official source).

1.2. Quality Goals

Prio Quality Goal Description

1

Ease of Use

Erpione must provide a seamless and intuitive experience for vendors, abstracting away the complexity of the E-Rezept ecosystem. The simulator must handle the intricate details of the complementary systems. This allows users to focus on developing and testing their own client logic without deep knowledge of the complementary systems.

2

End-to-End and Exploratory Testing

The architecture must minimise the overhead and friction involved in testing end-to-end workflows. Erpione must enable rapid feedback cycles and support both automated E2E and manual exploratory testing scenarios.

3

Maintainability and Adaptability

Erpione should be easy to maintain and extend, allowing for quick adaptation to changes in the E-Rezept specifications or the needs of different vendors. The architecture must support modular updates and clear separation of concerns.

2. Architecture Constraints

Erpione shall be:

  • plattform-independent and should run in containerized environments

  • designed to provide a REST API for integration with other test systems and tools

  • usable without real hardware components. Examples of these components include Konnektors and eHealth-Kartenlesegeräte, which are typically required for E-Rezept workflows. By simulating these components, Erpione allows vendors to test their applications without needing access to physical hardware, which can be costly and difficult to obtain for testing purposes.

  • modular and extensible to allow for future extensions and adaptations to different use cases

  • built on gematik’s shared test foundations rather than re-implementing the E-Rezept domain. Erpione reuses the E-Rezept E2E Testsuite, which in turn is based on the Bricks framework (B²riC²s). As a consequence Erpione inherits the Screenplay Pattern (actors, abilities, use cases) and the FHIR handling conventions defined there; see the Bricks User Manual for the underlying concepts and Building Block View for how the layers fit together.

3. Context and Scope

3.1. Business Context

Erpione acts as a "Primärsystem Simulator" for the E-Rezept ecosystem. Its primary function is to assist vendors in developing and testing client systems for the E-Rezept, ePA, and associated services by simulating the key interactions with the E-Rezept backend.

The business context includes:

  • Simulation of LEI (Leistungserbringende Institution):

    • PVS (Praxisverwaltungssystem)

    • AVS (Apothekenverwaltungssystem)

    • KTR (Kostenträger)

    • NCPeH (National Contact Point for eHealth)

  • Providing test data for end-to-end testing of E-Rezept workflows.

  • Providing test data randomization capabilities to support exploratory testing and robustness testing.

The business context does not include:

  • Simulation of FdV (Frontend des Versicherten).

  • Integration of real hardware components e.g. Konnektor.

Erpione uses an actor-based approach to model interactions. This concept is heavily inspired by the Screenplay Pattern with its Actor Model, which emphasizes using actors to represent different roles and responsibilities in a system. In this context, actors can be considered entities that perform actions and interact with the E-Rezept Fachdienst, thus facilitating the modeling of complex interactions in a clear, modular way. All Erpione actors are preconfigured with their own identity, derived from SMC-B, HBA and some additional configurations. A more detailed description of Erpione actors and their runtime handling is provided in Actor Model.

3.2. Technical Context

Erpione exposes its simulation capabilities via well-defined technical interfaces:

  • REST APIs: For interaction with the simulated client systems.

  • Web-based User Interface: For manual and exploratory testing.

Mapping Input/Output to Channels:

  • Domain-specific behaviours (e.g., prescription creation, claim, status updates) are mapped to REST endpoints.

  • The Erpione REST endpoints are primarily designed to communicate using the Hermes Data Model, a simplified JSON representation of the E-Rezept domain data which abstracts away the complexities of the underlying FHIR-based E-Rezept specifications.

  • For certain behaviours (e.g., creating prescriptions), Erpione may also support the use of FHIR resources as input. These resources are then directly used for the communication with the E-Rezept Fachdienst.

4. Solution Strategy

Erpione is primarily implemented in Java using the Spring Boot framework, which provides a robust foundation for building modular, maintainable, and production-grade services. The data model is defined in Kotlin, chosen for its seamless interoperability with Java, enhanced flexibility, and strong null-safety features, which help prevent common programming errors and improve code quality.

The system architecture follows the Backend-for-Frontend (BFF) pattern. Authentication is managed via Keycloak, which is integrated into the BFF layer to provide secure, standards-based identity management.

Deployment is handled using Docker Compose, targeting on-premise environments. This enables straightforward setup, reproducibility, and isolation of all required services, making it easy for vendors and testers to run Erpione in their own infrastructure.

These technology and architectural decisions directly support Erpione’s key quality goals: high operability and ease of use, reduced overhead for end-to-end testing, and maintainability. By abstracting the complexity of the E-Rezept ecosystem and providing a flexible, secure, and easy-to-deploy simulator, Erpione enables vendors to focus on their own development and testing tasks without being burdened by the details of complementary systems.

5. Building Block View

This section provides an overview of Erpione’s static architecture by describing its main building blocks, their responsibilities, and how they interact. Erpione itself is based on a layered and modular architecture which is heavily inspired by the Screenplay Pattern. The building blocks are designed to be cohesive, loosely coupled, and easily testable.

Erpione does not implement the E-Rezept domain itself but builds on two gematik libraries, each adding one layer of abstraction:

  • Bricks (B²riC²s) is the generic foundation. The Bricks framework provides reusable building bricks for maintainable test suites: the Screenplay core with actors, abilities and use cases shown in the diagram above, FHIR building bricks for profile-safe resource handling, and software abstractions for smartcards (HBA, SMC-B) and the Konnektor. Its concepts are documented in the Bricks User Manual.

  • E-Rezept E2E Testsuite is the domain layer built on Bricks. The E-Rezept E2E Testsuite contributes everything specific to the E-Rezept: the FHIR profiles of KBV, gematik and DAV, the client for the E-Rezept Fachdienst and the use cases such as prescribe, accept, dispense and close. It is the heart of the system and the place where the core functionality dealing with the Fachdienst is built and maintained.

  • Erpione exposes these capabilities as a service. It adds the REST API and the Web UI, the Hermes abstraction and the actor stage with preconfigured identities, so that the testsuite’s actors can be driven interactively or by external test systems.

Important Interfaces

The following interfaces are central to the interaction between Erpione’s building blocks and with external systems:

  • REST API: The main interface for client systems and the web frontend, exposing endpoints for prescription management, actor actions, and test data generation. Follows RESTful conventions and uses JSON (not FHIR) as the primary data format.

  • Data Model (Kotlin/Java Classes): Shared data structures used across the REST API, ensuring consistent serialization and deserialization of business objects. These classes form the Hermes Data Model, which abstracts away the complexities of the underlying FHIR while still supporting all necessary data for testing scenarios. The translation between the Hermes Data Model and FHIR is handled internally by the HermesService. Hermes and its capabilities are described in detail in Hermes.

  • FHIR Interface: Used internally and externally for E-Rezept data exchange, based on the HL7 FHIR standard. Ensures compatibility with the E-Rezept backend and client systems.

  • Authentication & Authorization (OAuth2/OpenID Connect): Integrates with Keycloak to secure API endpoints and the frontend, supporting OAuth2 and OIDC flows for user and system authentication.

  • Persistence Layer: Provides access to stored test data and simulation state via Spring Data JPA.

These interfaces are designed to be modular and extensible, supporting both automated and manual testing scenarios.

Motivation

The architecture of Erpione is heavily inspired by the Screenplay Pattern, which fosters maintainability, extensibility, and a strict separation of concerns. By structuring the system around clear roles and responsibilities — such as test data generation, API handling, and integration with the E-Rezept Fachdienst — Erpione enables users to focus on their specific development and testing needs without being burdened by the complexity of the entire E-Rezept ecosystem. The Screenplay Pattern’s emphasis on modularity and composability supports rapid adaptation to changes in specifications, facilitates the addition of new simulation features, and ensures that each component can be tested and evolved independently. Ultimately, this architectural approach helps Erpione fulfill its goal of providing a robust, user-friendly simulation environment for end-to-end testing and development.

6. Runtime View

Erpione’s runtime view illustrates how its main components interact during typical and critical scenarios. This section provides representative examples of end-to-end workflows, such as creation and dispensation of prescriptions. The focus is on the dynamic behaviour and communication between Erpione’s building blocks, supporting stakeholders in understanding operational and integration aspects without requiring deep knowledge of the static architecture.

6.1. Scope and Purpose

The runtime view focuses on the dynamic behaviour of Erpione during representative workflows.

  • What happens inside Erpione during a user-triggered action

  • How the REST API, frontend, authentication, and internal services collaborate

  • How Erpione communicates with the E-Rezept Fachdienst and related external systems

  • How runtime behaviour differs between full-stack and simplified deployments

The participants of the scenarios are the external systems introduced in Context and Scope — above all the E-Rezept Fachdienst and the complementary systems that take over a prescription during its lifecycle — and the building blocks described in Building Block View.

The prescription lifecycle itself (draft, ready, in-progress, completed, cancelled) is owned and enforced by the E-Rezept Fachdienst and is specified in the api-erp documentation. Erpione does not re-implement this state machine; it triggers the individual transitions on behalf of an actor. The Typical Runtime Flows below show which REST endpoint of Erpione maps to which Fachdienst operation along this lifecycle.

6.2. Recurring Runtime Concepts

The workflows described below are all composed of the same few cross-cutting concepts: actor resolution, Hermes translation, execution as an actor and local persistence. They are described once in Cross-cutting Concepts; the individual flows refer to them instead of repeating the details.

6.3. Typical Runtime Flows

All domain workflows in Erpione follow the same basic shape, regardless of whether they are triggered by the Web UI or by an automated client. A request arrives at the REST API together with an x-actor header; the controller resolves the actor from the actor stage and translates the payload from the Hermes Data Model (or takes a raw FHIR resource) into the FHIR resource required for the operation. The operation is then executed as the selected actor, which signs, authenticates and sends one or more FHIR operations to the E-Rezept Fachdienst. The response is translated back into the Hermes Data Model, stored locally and returned to the caller as JSON.

This means that Erpione itself does not implement the prescription lifecycle; the authoritative state of a prescription is always held by the Fachdienst. Erpione’s responsibility at runtime is to orchestrate the correct sequence of FHIR operations for a given actor role, hide the complexity of signing, authentication and FHIR profiling, and keep a local copy of the results so that clients and the Web UI can inspect them later.

The following subsections show this pattern for the most relevant scenarios: creating a prescription as a physician, taking over and dispensing a prescription as a pharmacy, and the two ways of reaching the REST API — interactively through the Web UI in a full-stack deployment and programmatically in a simplified REST-only deployment.

6.3.1. Prescription creation

A physician actor creates a pharmaceutical prescription with POST /api/erp/pharmaceutical. The request carries the x-actor header and an optional body; the direct query parameter switches to a direct assignment ("Direktzuweisung").

  1. The controller resolves the actor from the actor stage. Only actors with an HBA (physicians) are accepted here.

  2. The body is translated into a KBV prescription bundle:

    • Content-Type: application/json — the Hermes prescription payload is converted into FHIR. Omitted fields are faked so the resulting bundle still conforms to the active KBV profiles; an empty body therefore produces a complete random prescription.

    • Content-Type: application/fhir+xml — the body is taken as a FHIR template. An optional kvnr query parameter replaces the patient’s KVNR in the template.

  3. The controller selects the prescribe operation for the bundle and executes it as the resolved actor. The flow type (160, 169, 200, 209 or 166 for T-Rezept) is derived from the insurance kind in the bundle, the direct flag and the medication category.

  4. Executed as the actor, the operation performs two Fachdienst calls:

    1. Task/$create with the flow type — the Fachdienst returns a draft Task containing the prescription ID and access code.

    2. The KBV bundle is adjusted (prescription ID, current dates, MVO dates) and signed as QES with the actor’s HBA through the software Konnektor. Task/$activate uploads the signed bundle; the Fachdienst validates it and returns the activated Task (status ready).

  5. The activated task is translated back into the Hermes Data Model, enriched with the prescription data and the signature information, stored locally and returned as JSON. The response contains everything a pharmacy needs to claim the prescription (prescription ID and access code); a Data-Matrix-Code can be fetched afterwards with GET /api/erp/dmc/{pid}.

DiGA prescriptions (POST /api/erp/evdga, flow type 162) and the KTR use cases (/approve, /decline) as well as the EU pharmacy workflows under /api/eu follow exactly the same pattern with different operations towards the Fachdienst and are therefore not described separately.

6.3.2. Prescription claim, dispensation and close

A pharmacy actor takes over a prescription in up to three steps. All endpoints are located under /api/erp/{pid} and resolve the actor as an institution, i.e. an SMC-B is sufficient.

  1. Claim — POST /api/erp/{pid}/claim?ac=<accessCode> calls Task/$accept at the Fachdienst. The returned accept bundle contains the Task (now in-progress with a secret) and the signed KBV bundle. Erpione decodes the KBV bundle, translates both into the Hermes Data Model, stores them (overriding any already known data for this prescription) and returns the task including the secret.

  2. Dispense (optional) — POST /api/erp/{pid}/dispense calls Task/$dispense. The body is either Hermes JSON or FHIR XML describing the dispensed medication and is translated into the dispense parameters; if omitted, matching dispense data is generated. The Fachdienst keeps the task in-progress and Erpione returns an empty acknowledgement.

  3. Close — POST /api/erp/{pid}/close calls Task/$close with the close parameters (same input options as dispense). The Fachdienst completes the task and returns the signed receipt, which is translated into the Hermes Data Model, stored and returned. The raw FHIR receipt bundle can be re-fetched later with GET /api/erp/receipts/{pid}.

If a pharmacy cannot fulfil the prescription it can hand it back with POST /api/erp/{pid}/return (Task/$reject), and any involved institution can delete it with DELETE /api/erp/{pid}/abort (Task/$abort).

6.3.3. Manual exploratory workflow via Web UI

In the full-stack deployment a tester works with Erpione through the browser. The Web UI is a static single-page application served by its own Nginx container and reached through the reverse proxy under /ui. It never talks to the Erpione service directly; all calls go to /api/** on the reverse proxy, which forwards them to the OAuth2 BFF.

Whether the user has to authenticate depends on the deployment configuration:

  • Authentication enabled (default): the Erpione service runs as a stateless OAuth2 resource server and requires a valid JWT for every /api/** request. The BFF therefore redirects an unauthenticated browser to Keycloak (/oauth2/authorization/…​, /login), performs the OIDC authorization code flow, keeps the tokens in a server-side session and hands only a session cookie to the browser. For every subsequent /api call the BFF attaches the access token as Authorization: Bearer header before relaying the request to the Erpione service (token relay) and refreshes the token transparently when needed.

  • Authentication disabled: when the Spring profile noauth is active, the Erpione service permits all requests. This mode is intended for local or isolated test environments where Keycloak is not needed.

Once a request reaches the Erpione service, the processing is identical to the API workflow described above. The Web UI only provides a convenient way to select an actor (GET /api/actors), fill in Hermes payloads, trigger the prescribe/claim/dispense/close actions and inspect the persisted results (GET /api/erp/{pid}, GET /api/erp/prescriptions/{kvnr}, GET /api/erp/receipts). Actor resolution, Hermes translation and persistence are handled locally inside Erpione; only the FHIR operations themselves leave the deployment towards the Fachdienst via the SZZP.

6.3.4. Automated API workflow

An external test system drives Erpione purely via REST. In the simplified deployment the Erpione service exposes its REST API directly, typically with the noauth profile; in the full-stack deployment the client has to obtain a JWT from Keycloak and send it as bearer token (or go through the BFF like the Web UI does).

The request/response lifecycle for a single call is:

  1. The client sends an HTTP request to /api/erp/…​ with the x-actor header and, where applicable, the prescription ID in the path and ac / secret as query parameters.

  2. The controller resolves the actor, translates the body and executes the operation as the actor as described in the two prescription flows above.

  3. The response is always JSON in the Hermes Data Model (the task, the receipt or an empty acknowledgement) or an ErrorData payload in case of failure (see Error Handling). The only exception is GET /api/erp/receipts/{pid}, which returns the raw FHIR receipt bundle as application/fhir+xml.

The API is JSON-first: the Hermes Data Model is the primary and stable contract, while raw FHIR is accepted as input for selected endpoints (see Translation). In both cases the FHIR resources sent to the Fachdienst are built by Erpione; the client never communicates with the Fachdienst directly.

The results of these calls are stored locally so that the lookup endpoints and the Web UI can inspect them later; this local copy is a convenience cache and never the authoritative state of the prescription.

8. Cross-cutting Concepts

This section describes the concepts that span several building blocks of Erpione and recur in every runtime scenario. They are introduced once here so that the Building Block View and the Runtime View can refer to them instead of repeating the details: how clients exchange data with Erpione without having to deal with FHIR (Hermes), how actions are performed on behalf of a test actor (actor model), how results are kept locally (persistence), how failures are reported (error handling) and which connectivity Erpione needs towards the Telematikinfrastruktur.

8.1. Hermes – FHIR Abstraction

Hermes is Erpione’s FHIR abstraction: a domain-level data model together with the translation layer that maps it to and from FHIR. The name refers to the Greek messenger god who mediates between two worlds – here between the business view of a prescription and the FHIR representation required by the E-Rezept Fachdienst. Hermes consists of two parts:

  • The Hermes Data Model is the simplified representation of the E-Rezept domain data exposed by Erpione’s REST API as JSON. It describes prescriptions, dispenses, receipts and related business objects without any FHIR-specific semantics.

  • The HermesService is the translator that maps the Hermes Data Model to the FHIR resources expected by the E-Rezept Fachdienst, and FHIR responses back into the Hermes Data Model.

8.1.1. Hermes Data Model

The Hermes Data Model is implemented as plain Kotlin/Java classes which are shared across the REST API and serialised as JSON. The classes are designed to be simple and intuitive: they carry the business data a tester cares about – patient, prescriber, medication, dispense information – and leave out the structural and terminological ceremony of FHIR (bundles, references, profiles, codings). At the same time they support all data necessary for realistic testing scenarios, so that nothing relevant for the E-Rezept Fachdienst is lost in translation.

The main advantage of this decoupling is stability. The FHIR profiles of the E-Rezept are more likely to change over time than the business view of a prescription. A profile upgrade is therefore handled entirely inside the HermesService; the Hermes Data Model can stay stable even when the underlying FHIR profile version changes, and in many cases it does not need to change at all. The Hermes Data Model is the primary and stable contract of Erpione’s REST API.

8.1.2. Translation

Clients talk to Erpione in the Hermes Data Model, not in FHIR. Before an operation is executed, the HermesService translates the incoming payload into the FHIR resource the Fachdienst expects (for example a KBV prescription bundle or the parameters of a dispense). After the operation, the FHIR response of the Fachdienst is translated back into the Hermes Data Model before it is returned to the client. In both directions the FHIR resources that reach the Fachdienst are built by Erpione; the client never communicates with the Fachdienst directly.

FHIR stays optional rather than hidden. For selected endpoints (/pharmaceutical, /evdga, /dispense, /close) a client may alternatively send a raw FHIR resource with Content-Type: application/fhir+xml. Such a resource is taken as a template and used as-is, so that vendors can test their own FHIR resources against the Fachdienst without re-modelling them in the Hermes Data Model. Raw FHIR output is available where it is relevant for testing, e.g. the signed receipt bundle via GET /api/erp/receipts/{pid}.

8.1.3. Faker Capability

A second advantage of Hermes is its faker capability. When a data field is not relevant for a scenario, it can simply be omitted. Hermes fills the gap with a syntactically fitting, profile-conformant value, so that the resulting FHIR resource is still valid for the active profiles. Fields that are provided by the client are never overwritten. As a consequence an empty request body yields a complete, valid resource – for example a complete random prescription – which makes it possible to generate synthetic FHIR data sets that are accepted and processed by the E-Rezept Fachdienst.

The REST API provides dedicated /faker endpoints which you can use to play around with Hermes and inspect the generated data.

8.2. Actor Model

Erpione’s architecture is heavily inspired by the Screenplay Pattern: every business operation is performed by an actor. An ErpioneActor encapsulates the state and behaviour of a test actor – its identity (HBA or SMC-B), its role and everything needed to talk to the Telematikinfrastruktur. The ErpioneActorService manages the stage of actors and gives controllers a simple way to select and work with actors during a workflow. This keeps actor handling separate from request processing and domain logic.

8.2.1. Actor Roles

These are the main actor roles in the context of Erpione:

8.2.2. Actor Resolution

Every request to the REST API names the actor who shall perform the action via the x-actor header. The controller looks this actor up on the actor stage and checks that the actor’s role is suitable for the requested operation: creating a prescription requires a healthcare professional with an HBA (a physician), whereas pharmacy operations only require an institution with an SMC-B. An unknown or unsuitable actor is rejected before anything is sent to the Fachdienst (see Error Handling).

8.2.3. Execution as an Actor

The business operation itself is modelled as a use case that is performed by the resolved actor. Executing a use case as an actor means that the actor signs documents with its HBA or SMC-B through a software Konnektor, authenticates against the IdP and sends one or more FHIR operations to the E-Rezept Fachdienst on its own behalf. Controllers only decide which use case to run for whom; the actor encapsulates everything needed to actually talk to the Telematikinfrastruktur.

8.3. Local Persistence

The result of each operation is stored locally per prescription ID: the current task state together with access code, secret, prescription data and signature information after a prescribe or claim, and the receipt after a close. These stored copies feed the lookup endpoints (GET /api/erp/{pid}, GET /api/erp/prescriptions/{kvnr}, GET /api/erp/receipts) and the Web UI. They are a convenience cache only — the authoritative state of a prescription always lives in the Fachdienst — and expired prescriptions are purged periodically.

8.4. Error Handling

When an error occurs, Erpione represents it with ErrorData. The error payload contains an ErrorType that indicates whether the error originates in Erpione itself or in the Fachdienst. A human-readable message explains the problem, and optional issues can be included to narrow down the root cause.

So for example, if a prescription creation fails due to an invalid role of the actor, the ErrorType would indicate that the error is produced by the Fachdienst, and the issues would explain the root cause. In the following case for example we tried to create a prescription with an actor that has the wrong ProfessionOID, which is rejected by the Fachdienst:

{
    "message": "Actor Telesphorus expected a response of type 'ErxTask' but received 'OperationOutcome' instead",
    "type": "FACHDIENST",
    "issues": [
        {
            "severity": "Error",
            "details": "The QES-Certificate does not have expected ProfessionOID."
        }
    ]
}

Or if try to claim a prescription which is unknown to the Fachdienst, the Fachdienst would reject the request with an OperationOutcome and Erpione would return the following error payload to the client system:

{
  "message": "Actor Hygieia expected a response of type 'ErxAcceptBundle' but received 'OperationOutcome' instead",
  "type": "FACHDIENST",
  "issues": [
    {
      "severity": "Error",
      "details": "Task not found for prescription id"
    }
  ]
}

While on the other hand, if Erpione itself fails to process a request or runs into an internal error, the ErrorType would indicate that the error is produced by Erpione, and the issues would explain the root cause. In the following case for example when we try to call a REST endpoint that is not implemented, Erpione would return the following error payload to the client system:

{
  "message": "No static resource api/erp/claim/160.000.114.452.028.14.",
  "type": "ERPIONE",
  "issues": [
    {
      "severity": "ERROR",
      "details": "No controller found for: POST api/erp/claim/160.000.114.452.028.14"
    }
  ]
}

Or if we try to perform an action with an actor that is not present in the stage of actors or not allowed for this operation, Erpione would return the following error payload to the client system:

{
  "message": "No such actor with id 'Erpione'",
  "type": "ERPIONE",
  "issues": [
    {
      "severity": "ERROR",
      "details": "ActorNotFoundError: No such actor with id 'Erpione'"
    }
  ]
}

The following diagram illustrates the two error categories. In the first case the Fachdienst rejects the request with an OperationOutcome; the actor raises an ErpResponseExpectationError, which the central ErpioneErrorHandler (@ControllerAdvice) translates into ErrorData of type FACHDIENST, preserving the Fachdienst status code and issues. In the second case Erpione itself fails before contacting the Fachdienst (here: unknown actor), and the error handler returns ErrorData of type ERPIONE.

8.5. TI Connectivity

Erpione is designed to communicate with the E-Rezept Fachdienst and therefore needs TI connectivity. The api-erp documentation provides one detailed way to set this up in TI-Konfiguration, but other connectivity solutions may also be possible depending on the deployment environment.

Independent of the chosen route, the Fachdienst identifies the calling system via the User-Agent header. Patient actors (simulating the FdV) additionally communicate via the Internet route and require an X-api-key. These credentials are not shipped with Erpione; operators have to provide their own values as described in E-Rezept Fachdienst Credentials (application-secrets.yaml).

9.5.2. E-Rezept Fachdienst Credentials (application-secrets.yaml)

Every request towards the E-Rezept Fachdienst must carry a User-Agent header that identifies the Primärsystem. Patient actors (simulating the FdV / E-Rezept app) use the Internet route and additionally require an X-api-key header. Both values are environment-specific credentials and are therefore not part of the public repository: the file application-secrets.yaml is excluded via .githubignore, and the public source tree does not contain it.

The server nevertheless expects these values. application.yaml includes the Spring profile secrets (spring.profiles.include), which makes Spring Boot load application-secrets.yaml next to the other application-*.yaml files when present. Operators running their own Erpione instance must supply this file (or equivalent configuration) themselves.

The credentials are per environment profile (see Spring Boot Profiles) and live below erpione.environment:

Property Required Description

erpione.environment.ti.userAgent

yes

User-Agent sent on the TI route (split-DNS endpoints via SZZP/Konnektor). Format defined by gematik, e.g. <ProductName>/<Version> <VendorID>

erpione.environment.internet.userAgent

Patient actors only

User-Agent sent on the Internet route, which is used by patient actors (simulating the FdV / E-Rezept app)

erpione.environment.internet.xapiKey

Patient actors only

X-api-key for the Internet endpoints of the Fachdienst (erp-*.app.ti-dienste.de). Only required when patient actors (FdV simulation) are used; doctors and pharmacies communicate via the TI route exclusively.

Create erpione-server/src/main/resources/application-secrets.yaml from the following template and fill in your own values for every environment you intend to use. The --- separated documents are activated per profile via spring.config.activate.on-profile:

---
spring:
  config:
    activate:
      on-profile: tu
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-tu-x-api-key>"
      userAgent: "<your-user-agent>"

---
spring:
  config:
    activate:
      on-profile: ru
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-ru-x-api-key>"
      userAgent: "<your-user-agent>"

---
spring:
  config:
    activate:
      on-profile: rudev
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-rudev-x-api-key>"
      userAgent: "<your-user-agent>"

Alternatively, the values can be provided without touching the source tree, e.g. as environment variables for the erpione-server container (ERPIONE_ENVIRONMENT_INTERNET_XAPIKEY, ERPIONE_ENVIRONMENT_TI_USERAGENT, ERPIONE_ENVIRONMENT_INTERNET_USERAGENT) or through an external config location (SPRING_CONFIG_ADDITIONAL_LOCATION). Standard Spring Boot property precedence applies.

Obtaining credentials

The X-api-key and the agreed User-Agent for the gematik test environments (TU, RU, RU-DEV) are issued on request by gematik. Please contact gematik Fachportal and state the environments you need access to.

WARNING: Treat application-secrets.yaml like any other secret: never commit it to a public repository and keep it out of Docker images that are shared outside your organisation.

9.6.2. Local Development Workflow

This workflow is intended for local development and testing only; it is not suitable for production environments.

To reduce OAuth2 complexity during development, the local stack runs without Keycloak and without the OAuth2 BFF. Authentication is therefore disabled in this setup.

Contrary to the two possible Deployment Views the local Development Workflow is mostly the full deployment stack without the authentication server and the BFF. The local development workflow is intended for developers to quickly test changes in the backend or frontend without having to deal with the complexity of OAuth2 and Keycloak.

The erpione-server artifact must be built and repackaged before deployment; see Building Java/Kotlin Modules for the required ./mvnw package spring-boot:repackage -f erpione-server/pom.xml -DskipTests step. 
#!/bin/bash
set -e

ensure_volume() {
  local volume_name="$1"
  if ! docker volume inspect "$volume_name" >/dev/null 2>&1; then
    docker volume create "$volume_name" >/dev/null
    echo "Created volume: $volume_name"
  else
    echo "Volume already exists: $volume_name"
  fi
}

cd $(git rev-parse --show-toplevel)

# 1. Set environment
export ENVIRONMENT=rudev
export ERP_FHIR_PROFILE=1.6.0
export ACTIVE_SPRING_PROFILES=${ENVIRONMENT},noauth
export PUBLIC_PORT=8080

# 2. Create required Docker volumes
ensure_volume "erpione-data-${ENVIRONMENT}"

# 3. Build and start containers
docker compose -f dc-erpione-local.yml up -d --build

# 4. Wait for services to be healthy
echo "Waiting for services to start..."
sleep 15

# 5. Verify health
docker compose -f dc-erpione-local.yml ps

Now you can access the local development stack at localhost:8080. The REST API is available at localhost:8080/api/info.

#!/bin/bash

echo "=== Erpione Health Check ==="

# Function to check HTTP endpoint
check_http() {
  local endpoint=$1
  local name=$2
  echo -n "Checking $name ($endpoint)... "
  if curl -s -f "$endpoint" > /dev/null; then
    echo "✓ OK"
  else
    echo "✗ FAILED"
    return 1
  fi
}

# Function to check container
check_container() {
  local container=$1
  echo -n "Checking container $container... "
  if docker ps --filter "name=$container" --filter "status=running" | grep -q "$container"; then
    echo "✓ Running"
  else
    echo "✗ Not running"
    return 1
  fi
}

check_http "http://localhost:8080/actuator/health" "Resource Server"
check_http "http://localhost:8080/kc/health/ready" "Keycloak"

check_container "erpione-resource-server"
check_container "erpione-bff"
check_container "erpione-redis"
check_container "erpione-keycloak"
check_container "erpione-reverse-proxy"
