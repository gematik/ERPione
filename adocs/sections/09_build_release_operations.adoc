[[section-build-release-operations]]
== Build, Release & Operations

This section covers the build process, deployment procedures, and operational aspects necessary to set up and maintain Erpione in your own infrastructure.

=== Overview

Erpione is a distributed system composed of multiple modules written mainly in Java and Kotlin. The build and deployment process involves:

* Building multiple Maven modules (Java/Kotlin backend components)
* Creating Docker container images for each service
* Orchestrating containers via Docker Compose
* Managing secrets and configuration

[[section-prerequisites]]
=== Prerequisites

==== System Requirements

[options="header",cols="1,3"]
|===
| Component | Requirement

| Docker
| Minimum version: 29.5.3 (tested and recommended). Older versions may work but without guarantees.
Docker Engine with Docker Compose (v2.0+). See link:https://docs.docker.com/engine/install/[Docker Installation Guide]

| Memory
| **Without authentication (no Keycloak/BFF):** Minimum 1GB+

**With full stack (Keycloak + BFF):** Minimum 2.5GB, Recommended 3GB+

Total stack consumption is approximately 2.5GB with authentication enabled. Keycloak and BFF are the primary memory consumers. Allocate 3GB+ for comfortable operation and headroom.

| Network
| Connectivity to TI (telematics infrastructure) environments
Proxy/SZZP access for production deployments (see <<section-deployment-view>>)

|===

==== Build Tools

[options="header",cols="1,2,3"]
|===
| Tool | Version | Usage

| Java Development Kit (JDK)
| 21
| Required for building and running all backend services (erpione-server, erpione-oauth2-bff)

| Maven
| 3.9.0+ (bundled via `./mvnw`)
| Used to build Java/Kotlin modules. The repository includes the wrapper script `./mvnw`.

| Git
| Latest
| For cloning the repository

|===

==== Supported Operating Systems

The only hard requirement is **Java 21 capable JVM** and **Docker**. Erpione runs in containers, so the underlying OS is largely irrelevant.

- **Linux**: Any distribution capable of running Java 21 and Docker (Ubuntu, Debian, RHEL, CentOS, Fedora, Rocky Linux, AlmaLinux, etc.)
- **macOS**: Any version that supports Java 21 JVM (M1/M2 ARM64 and Intel architectures supported)
- **Windows**: Windows 10/11 with WSL2 backend (to provide Linux kernel and Docker support). Requires Java 21 JVM in WSL2 environment

=== Build Process

==== Repository Structure

[source]
----
erpione-application/
├── erpione-server/              # Main REST API service (Spring Boot, Java/Kotlin)

==== Building Java/Kotlin Modules

[[section-rebuild-all-modules]]
===== Full Build (all modules)

[source,shell]
----
cd $(git rev-parse --show-toplevel)

# Clean and build all modules, skip tests
./mvnw clean install -DskipTests

# Package the main erpione-server JAR
./mvnw package spring-boot:repackage -f erpione-server/pom.xml -DskipTests
----

===== Build Individual Modules

[source,shell]
----
# Build only the server
./mvnw clean package -f erpione-server/pom.xml -DskipTests

# Build only the BFF
./mvnw clean package -f erpione-oauth2-bff/pom.xml -DskipTests

# Build only the CLI
./mvnw clean package -f erpione-cli/pom.xml -DskipTests
----

===== Build Artifacts

After successful build, look for:

[options="header",cols="2,3"]

| erpione-server
| `erpione-server/target/erpione-server-*.jar`

| erpione-oauth2-bff
| `erpione-oauth2-bff/target/oauth2-bff-*.jar`

==== Building Frontend

The frontend consists of static HTML and JavaScript files served directly by Nginx. No framework (Vue, React, etc.) or build compilation is required.

===== Frontend Structure

The `erpione-frontend/` directory contains:

- Static HTML files
- JavaScript files
- CSS stylesheets  
- Images and assets
- Nginx configuration (`default.conf`, `entrypoint.sh`)

===== Frontend Deployment

The frontend files in `erpione-frontend/dist/` are copied directly into the Nginx container during image build:

[source,dockerfile]
----
FROM nginx:alpine
COPY dist/ /usr/share/nginx/html/
----

**No build step is required** for the frontend. The static files are served as-is.

**To update the frontend:**

1. Modify HTML, CSS, or JavaScript files in `erpione-frontend/`
2. Rebuild the Nginx container: `docker compose -f dc-erpione-local.yml build ui`
3. Or copy updated files directly to running container: `docker cp ./erpione-frontend/dist/. erpione-ui-${ENVIRONMENT}:/usr/share/nginx/html/`

[[section-fachdienst-credentials]]
==== E-Rezept Fachdienst Credentials (`application-secrets.yaml`)

Every request towards the E-Rezept Fachdienst must carry a `User-Agent` header that identifies the Primärsystem. Patient actors (simulating the FdV / E-Rezept app) use the Internet route and additionally require an `X-api-key` header. Both values are environment-specific credentials and are therefore **not** part of the public repository: the file `application-secrets.yaml` is excluded via `.githubignore`, and the public source tree does not contain it.

The server nevertheless expects these values. `application.yaml` includes the Spring profile `secrets` (`spring.profiles.include`), which makes Spring Boot load `application-secrets.yaml` next to the other `application-*.yaml` files when present. Operators running their own Erpione instance must supply this file (or equivalent configuration) themselves.

The credentials are per environment profile (see <<section-spring-profiles>>) and live below `erpione.environment`:

[options="header",cols="2,1,3"]
|===
| Property | Required | Description

| `erpione.environment.ti.userAgent`
| yes
| `User-Agent` sent on the TI route (split-DNS endpoints via SZZP/Konnektor). Format defined by gematik, e.g. `<ProductName>/<Version> <VendorID>`

| `erpione.environment.internet.userAgent`
| Patient actors only
| `User-Agent` sent on the Internet route, which is used by patient actors (simulating the FdV / E-Rezept app)

| `erpione.environment.internet.xapiKey`
| Patient actors only
| `X-api-key` for the Internet endpoints of the Fachdienst (`erp-*.app.ti-dienste.de`). Only required when patient actors (FdV simulation) are used; doctors and pharmacies communicate via the TI route exclusively.
|===

Create `erpione-server/src/main/resources/application-secrets.yaml` from the following template and fill in your own values for every environment you intend to use. The ``---`` separated documents are activated per profile via `spring.config.activate.on-profile`:

[source,yaml]
----
---
spring:
  config:
    activate:
      on-profile: tu
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-tu-x-api-key>"
      userAgent: "<your-user-agent>"

---
spring:
  config:
    activate:
      on-profile: ru
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-ru-x-api-key>"
      userAgent: "<your-user-agent>"

---
spring:
  config:
    activate:
      on-profile: rudev
erpione:
  environment:
    ti:
      userAgent: "<your-user-agent>"
    internet:
      xapiKey: "<your-rudev-x-api-key>"
      userAgent: "<your-user-agent>"
----

Alternatively, the values can be provided without touching the source tree, e.g. as environment variables for the `erpione-server` container (`ERPIONE_ENVIRONMENT_INTERNET_XAPIKEY`, `ERPIONE_ENVIRONMENT_TI_USERAGENT`, `ERPIONE_ENVIRONMENT_INTERNET_USERAGENT`) or through an external config location (`SPRING_CONFIG_ADDITIONAL_LOCATION`). Standard Spring Boot property precedence applies.

Obtaining credentials::
The `X-api-key` and the agreed `User-Agent` for the gematik test environments (TU, RU, RU-DEV) are issued on request by gematik. Please contact https://fachportal.gematik.de/[gematik Fachportal] and state the environments you need access to.

**WARNING**: Treat `application-secrets.yaml` like any other secret: never commit it to a public repository and keep it out of Docker images that are shared outside your organisation.

==== Local Development Workflow

This workflow is intended for local development and testing only; it is not suitable for production environments.

To reduce OAuth2 complexity during development, the local stack runs without Keycloak and without the OAuth2 BFF. Authentication is therefore disabled in this setup.

Contrary to the two possible <<section-deployment-view,Deployment Views>> the local Development Workflow is mostly the full deployment stack without the authentication server and the BFF. The local development workflow is intended for developers to quickly test changes in the backend or frontend without having to deal with the complexity of OAuth2 and Keycloak.

NOTE: The `erpione-server` artifact must be built and repackaged before deployment; see <<section-build-process,Building Java/Kotlin Modules>> for the required `./mvnw package spring-boot:repackage -f erpione-server/pom.xml -DskipTests` step.


[source,shell]
----
#!/bin/bash
set -e

ensure_volume() {
  local volume_name="$1"
  if ! docker volume inspect "$volume_name" >/dev/null 2>&1; then
    docker volume create "$volume_name" >/dev/null
    echo "Created volume: $volume_name"
  else
    echo "Volume already exists: $volume_name"
  fi
}

cd $(git rev-parse --show-toplevel)

# 1. Set environment
export ENVIRONMENT=rudev
export ERP_FHIR_PROFILE=1.6.0
export ACTIVE_SPRING_PROFILES=${ENVIRONMENT},noauth
export PUBLIC_PORT=8080

# 2. Create required Docker volumes
ensure_volume "erpione-data-${ENVIRONMENT}"

# 3. Build and start containers
docker compose -f dc-erpione-local.yml up -d --build

# 4. Wait for services to be healthy
echo "Waiting for services to start..."
sleep 15

# 5. Verify health
docker compose -f dc-erpione-local.yml ps
----

Now you can access the local development stack at `http://localhost:8080`. The REST API is available at `http://localhost:8080/api/info`.

==== Manual Health Check Script

[source,shell]
----
#!/bin/bash

echo "=== Erpione Health Check ==="

# Function to check HTTP endpoint
check_http() {
  local endpoint=$1
  local name=$2
  echo -n "Checking $name ($endpoint)... "
  if curl -s -f "$endpoint" > /dev/null; then
    echo "✓ OK"
  else
    echo "✗ FAILED"
    return 1
  fi
}

# Function to check container
check_container() {
  local container=$1
  echo -n "Checking container $container... "
  if docker ps --filter "name=$container" --filter "status=running" | grep -q "$container"; then
    echo "✓ Running"
  else
    echo "✗ Not running"
    return 1
  fi
}

check_http "http://localhost:8080/actuator/health" "Resource Server"
check_http "http://localhost:8080/kc/health/ready" "Keycloak"

check_container "erpione-resource-server"
check_container "erpione-bff"
check_container "erpione-redis"
check_container "erpione-keycloak"
check_container "erpione-reverse-proxy"

echo "=== Health Check Complete ==="
----
